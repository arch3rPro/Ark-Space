# Optional managed WeKnora connection

- **Status:** accepted; implemented in unreleased source with automated Linux qualification; human UX, real services and hosted OS acceptance unverified
- **Class:** execution and credentials
- **Extends:** [ADR 0009](0009-local-credential-setup.md)

WeKnora supports two execution paths. Users may configure `WEKNORA_BASE_URL` and `WEKNORA_API_KEY` themselves and use the Skill without installing `arks`. Alternatively, `arks setup` may manage a connection and credentials, with `arks` executing explicitly supported WeKnora operations internally. Managed execution is optional, not a mandatory Skill dependency. The user approved this boundary and authorized completing the remaining Setup, runtime, and Skill integration together. Managed operations cover verification, knowledge-base list/detail, and single-base search; imports, document/chunk operations, multi-base search, and chat remain independent environment operations.

The Skill must not parse private ArkSpace configuration or obtain raw credentials from CLI output. WeKnora is a knowledge-base connection, not a Web search Provider: it does not join search order, key rotation, or cross-instance fallback. The environment-only Skill remains independently usable after managed support is implemented.

This preserves independent Skill installation while providing a secure optional onboarding path. It rejects both a mandatory CLI dependency and a Setup-only credential store that the Skill cannot actually use. The implementation contract and qualification evidence are recorded in the [WeKnora managed configuration spec](../../../.scratch/weknora-managed-config/spec.md). This extends [ADR 0017](0017-workbench-modal-setup.md) with a WeKnora connection context while retaining its three focus regions, Web Provider behavior, and global order/language. The connection has its own form and actions, no enablement/rotation/order semantics; all five service labels are shown when the header has room, otherwise a width-based window keeps the selected service visible without moving other panes; `w` also advertises access from Web pages. The WeKnora configuration list marks API address/key as required and default knowledge-base ID as optional, with single-field editing even when empty, and no configure-all form. Incomplete values remain only in the owned Setup session, are explicitly temporary, and ordinary exit requires Cancel-default discard confirmation; completing the valid pair writes the connection normally. Key rows reuse the trusted-terminal masked-default preview. Source metadata belongs in concise details. The user rejected menu compaction: retain the original 19-cell menu and fix URL/reference, source and status column allocation directly without changing navigation semantics. Saving stays offline; an explicit request to read the configured instance authorizes network access. HTTP is supported with an informational plaintext-transport warning.

The user explicitly removed the WeKnora private/nonpublic IP restriction and its CIDR/access-setting UI. It was an extra ArkSpace client policy, not a WeKnora API prerequisite. The trusted configured WeKnora destination may be public, private or loopback; fixed authenticated routes accept it without an IP grant. Valid legacy `allowRanges` fields remain loadable but do not authorize or block WeKnora traffic and are cleared on new saves. Generic public-web HTTP and SearXNG retain their separate address-denial/exception rules. WeKnora still validates the exact configured origin, all DNS answer IP formats and pinned lookup, TLS certificates, route/input/response boundaries, redirects/proxies, consent, cancellation and deadlines. It remains neither an arbitrary authenticated proxy nor a cross-source credential fallback.
